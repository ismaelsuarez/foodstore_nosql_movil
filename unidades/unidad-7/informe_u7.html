A. Modelo y alcance

El trabajo continúa el modelo relacional de foodstore_baseII, etiqueta u6-cierre, commit 8f7877c8a1ff25c1be28b29c46c38cd7c9663e86. El modelo de origen tiene cinco tablas: categoria, usuario, producto, pedido y detalle_pedido. El subconjunto migrado es «pedidos y detalle de pedidos»: los pedidos 1–5 y sus 7 líneas, leídos de la base foodstore (PostgreSQL 17.11) con datos del usuario y del producto. El destino es la colección foodstore_u7.pedidos, con un documento por pedido. Las decisiones de modelo son del equipo, no de la consigna (E3).

Por qué se embebe. Las cuatro consultas filtran y devuelven pedidos como unidad. C4a lista los pedidos del lote con una proyección parcial (_id y estado); C4b filtra por estado; C4c busca un producto dentro de las líneas; C4d filtra por total con otra proyección parcial (_id y total). Ninguna de las dos devuelve el pedido completo. El embebido responde al acceso frecuente declarado, que es recuperar el pedido completo: con el cliente y las líneas en el mismo documento, ese pedido se obtiene en una sola lectura y se escribe de forma atómica por documento. El costo es duplicar nombres de cliente y de producto como copia, sin actualización automática.

Bajas lógicas. Se conservan todos los pedidos y todas las líneas con su indicador. C4b, C4c y C4d exigen eliminado: false en el pedido, y C4c exige además una línea vigente del producto en el mismo elemento. El total es la suma de los subtotales de las líneas no eliminadas. En este lote no hay bajas lógicas (E3, E4).

Datos. Los usuarios 1–3 son sintéticos del seed U6: Ana Gómez, Luis Paz y Marta Ruiz. Se compararon con el seed antes de exportarlos. No se trasladan mail, celular, contraseña ni rol (E4).

C. Consultas y comparación

Líneas 23, 31, 36–39, 45–48 y 53–56 de mongodb/consultas_mongodb.js, copiadas sin cambios:

const lote = { _id: { $in: ['1', '2', '3', '4', '5'].map((id) => NumberLong(id)) } };
const c4a = pedidos.find(lote, { _id: 1, estado: 1 }).sort({ _id: 1 }).toArray();
const c4b = pedidos.find(
  { ...lote, eliminado: false, estado: 'TERMINADO' },
  { _id: 1 }
).sort({ _id: 1 }).toArray();
const c4c = pedidos.find(
  { ...lote, eliminado: false, items: { $elemMatch: { producto_id: NumberLong('1'), eliminado: false } } },
  { _id: 1 }
).sort({ _id: 1 }).toArray();
const c4d = pedidos.find(
  { ...lote, eliminado: false, total: { $gt: NumberDecimal('3000.00') } },
  { _id: 1, total: 1 }
).sort({ _id: 1 }).toArray();

Fragmento de postgresql/consultas_postgresql.sql (C4c; C4b usa el mismo lote y el mismo filtro de baja, con p.estado = 'TERMINADO'):

SELECT 'C4c' AS consulta,
       count(*) AS cantidad,
       string_agg(p.id::text, ',' ORDER BY p.id) AS pedidos
FROM pedido p
WHERE p.id IN (1, 2, 3, 4, 5)
  AND p.eliminado = FALSE
  AND EXISTS (
      SELECT 1
      FROM detalle_pedido dp
      WHERE dp.pedido_id = p.id
        AND dp.producto_id = 1
        AND dp.eliminado = FALSE);

Las consultas PostgreSQL corren en una transacción REPEATABLE READ, READ ONLY con ROLLBACK. EXISTS cuenta cada pedido una sola vez; en MongoDB, $elemMatch exige el producto y la línea vigente en el mismo elemento.

D. Contraste de IA y conclusión

Consulta (consigna 6). El prompt pidió comparar PostgreSQL y MongoDB para los pedidos de Food Store. Describía el modelo relacional de cinco tablas con claves, restricciones y lógica para subtotales y totales, y la colección con cliente e items embebidos, IDs Long, Int32, Decimal128 y precios históricos. Mencionaba el acceso frecuente al pedido completo y la necesidad de cantidades positivas, subtotales coherentes y total de líneas vigentes. Pedía ventajas, costos y responsabilidades de integridad, separar las capacidades del motor de lo implementado y no afirmar rendimiento no medido ni carencias de transacciones o validación. El texto completo y la respuesta están en E6.

La respuesta la generó Claude Opus 5.5 el 2026-11-06, en la misma sesión del asistente que implementó la migración. Por eso no es una consulta independiente. Se guardó antes de leer las fuentes del contraste.

Afirmación de la respuestaFuente y qué respaldaEvaluación
A1. insertMany con varios documentos no es atómico para el lote; la atomicidad entre documentos requiere transacciones en un replica set o un clúster fragmentado; una instancia standalone no las admite. F1: cada documento es atómico, pero «the operation as a whole is not atomic». F6, sección Availability: «standalone deployments do not support transactions». F1 no dice literalmente que lo ya insertado permanece. Respaldada documentalmente; no ensayada: no se probó un fallo parcial ni una transacción. El primer veredicto fue «necesita matiz», sin F6.
A2. Un CHECK evalúa solo la fila insertada o actualizada; no puede comparar pedido.total con la suma de detalle_pedido, que depende de lógica programable. F5: PostgreSQL no admite CHECK que referencien datos distintos de la fila comprobada. Los CHECK de schema.sql cubren reglas de una fila (cantidad > 0, importes ≥ 0). El total agregado lo mantienen las funciones y los disparadores del TPI (tpi/sql/objetos_programables.sql), conservados en u6-cierre, que declaran límites ante DML concurrente directo y escritura directa del total. Respaldada. Consecuencia: el diseño copia el total y lo verifica (RI-02), sin recalcularlo.

Constraints, nota de Check Constraints: postgresql.org/docs/17/ddl-constraints.html · F6 MongoDB Manual, Production Considerations, sección Availability: mongodb.com/docs/manual/core/transactions-production-consideration/. Conclusión (consigna 7) — propuesta pendiente de revisión del equipo; 186 palabras.

Proponemos mantener PostgreSQL como fuente principal de los pedidos y usar MongoDB solo como copia documental de lectura de este subconjunto, si el acceso al pedido completo lo justifica.

Integridad: en PostgreSQL, las claves foráneas y las restricciones CHECK rechazan en cada escritura líneas sin producto o cantidades no positivas, y los disparadores del TPI mantienen el total agregado, con límites declarados. En la colección, RI-01 y RI-02 se verificaron con scripts después de la carga; no se instalaron validadores permanentes.

Forma de acceso: cada documento contiene cliente e items, devuelve el pedido completo en una sola lectura y se escribe de forma atómica por documento, no por lote. Se conservaron IDs Long, cantidades Int32, importes Decimal128 y precios históricos; C4b y C4c devolvieron los mismos pedidos en ambos motores.

Duplicación: los nombres de cliente y de producto son copias; la coincidencia entre motores se verificó el 2026-11-06 y no implica sincronización.

El lote tiene cinco pedidos, un solo estado y ninguna baja lógica, y no se midió rendimiento. Ampliar el uso de MongoDB exigiría pruebas con más volumen y una carga reproducible desde el origen.

Uso de IA y decisiones humanas. Kiro se usó para especificar y Claude para implementar, documentar, generar la respuesta contrastada y redactar este informe; ambas herramientas fueron autorizadas por el docente. El equipo decidió, mediante encargos explícitos, el modelo, el lote y sus parámetros, el uso de MongoDB 9.0.4 y cada autorización de ejecución. El contraste, la conclusión y este informe siguen pendientes de revisión del equipo.

Limitaciones.

  • Cinco pedidos, un solo estado (TERMINADO) y ninguna baja lógica: C4b devuelve el lote completo y los filtros sobre eliminado no se ponen a prueba.
  • Sin mediciones de rendimiento.
  • Sin validadores permanentes.
  • Sin prueba de fallo parcial de insertMany ni de transacciones.
  • La coincidencia entre motores es una verificación puntual, no una sincronización.
  • La respuesta de IA no es independiente.
